# Luna room selector: diagnostic, not a benchmark win

On 2026-09-26, `gpt-6-luna` at `xhigh` effort built [index.html](index.html) from the frozen [brief](prompt.md) in an isolated empty directory after reading the Seenry and Seenry Motion entrypoints by absolute path. The run used the working tree before the responsive-review correction recorded below; it was not a frozen release comparison. Codex reported 122,201 tokens. Its own browser check covered desktop selection and keyboard behavior; it explicitly reported that it could not inspect a narrow viewport.

Independent Chromium checks after the run exercised 320, 768 and 1440 CSS-pixel widths. At all three sizes, selecting Room C, choosing 11:30, changing to Room B, and opening/closing the local review kept the selected time, updated the total from $75 to $55, and displayed truthful local-simulation language. No runtime errors or horizontal overflow were observed. An axe-core WCAG A/AA scan of the initial 320px state returned no violations. These checks do not establish screen-reader usability, physical-device performance, or design quality.

The [desktop render](desktop-final.png) has a legible comparison and a coherent audio-studio motif. The [320px render](mobile-final.png) exposes a visual failure: the 156px sticky summary sits over the room list in the initial viewport, hiding part of the comparison. Pointer tests can still reach the options by scrolling, but that is a weaker experience than the task requires. The run is therefore **needs revision** on responsive finish. No claim of superiority over another skill follows from this single, unpaired case.

The observed defect led to an explicit narrow-viewport occlusion check in Seenry's production review. The next evaluation should freeze that revision, use fresh briefs, include both desktop and narrow rendered review, and compare anonymous outputs under matched model and tool conditions. Preserve this failed state as development evidence rather than presenting it as a successful example.
