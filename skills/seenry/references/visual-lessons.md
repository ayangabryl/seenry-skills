# Learn a decision from rendered alternatives

Use one or two relevant lessons before resolving an uncertain visual decision. Run `python scripts/lesson_packet.py TOPIC [TOPIC]` relative to the installed Seenry directory. Topics: state, hierarchy, color, enclosure, controls, continuity, finish, packing-preference, export-feedback, editing-frame. The packet identifies actual screenshots and, for authored exercises, source HTML under `references/lessons/`; inspect them with available image/browser tools. They work without MCP or an image generator. The original exercises include local Inter/Lucide assets for rendering.

Each lesson contains a question, a controlled comparison, a transfer mechanism and a countercase. Original exercises are **authored teaching hypotheses**. The separately identified blind preferences and rejected outputs have actual human labels with their stated limits; this collection is not a validated preference dataset. Learn a relationship; do not reuse their fictional brands, palette or composition by default. The state study follows a rejected listening-queue result; it belongs to development evidence and cannot be a fresh holdout benchmark.

The separate **finish** case preserves a real blind preference for one of two Flash-generated schedulers, recorded in `lessons/finish-preference.json`. Multiple variables differ; it is not a controlled single-property study. One person's preference does not certify every detail or establish population-wide taste. Once included here, the scheduler belongs to development evidence, not an unseen evaluation task.

| Decision | Inspect for | Preserve in a different brief |
| --- | --- | --- |
| state | Necessary information versus repeated emphasis | Visible selection, action names and keyboard focus have different jobs |
| hierarchy | Content roles and grouping before weight or decoration | Reading order, comparable data and appropriate density |
| color | Competing accents versus deliberate occupied areas | Non-color state information; colorful content can stay colorful |
| enclosure | Nested borders, label/input proximity and inset relationships | Focus visibility and region boundaries that help the task |
| controls | Persistent emphasis versus quiet familiar actions | Discoverability, real icons and usable hit areas |
| continuity | Same identity through geometry change and rapid reversal | Current business state, stable text and reduced-motion access |

For continuity, operate the HTML and watch a recording. The stills show only settled layout. For any pair, a choice of equal, reject-all or unverified is valid. A letter is not an answer key. The teaching mechanism is a hypothesis to test on the project's own content.

Before expanding a project, resolve one **representative finished slice** with its real copy, type, material, controls, narrow layout and decisive transition. Retain the selected relationships in DESIGN.md. A wireframe establishes geometry, not final visual quality. Review the built slice again against its evidence; implementation can lose the selected character.

## Review the reviewer

Use `scripts/reviewer_probe.py prepare` to create an anonymous, shuffled image set from a local manifest. A case requires id, brief, question and variants with id/image. The private mapping and human labels remain outside the reviewing context. Ask for preferred A/B/etc., equal, reject-all or unverified, an observation and one repair. Repeat with a different order, normalize using the private keys, then compare.

Order consistency is a diagnostic. Correctness needs independent task evidence or actual human judgments; authored preferences must not become human labels. Test repairs by rendering the smallest proposed change and checking useful information/behavior was preserved. Once a case informs guidance, move it into development and preserve its earlier held-out history. A new review context does not undo dataset leakage.

The **export-feedback** lesson contains two real Luna outputs rejected by the user despite model visual passes. Read its scoped feedback and inspect both ordinary and narrow captures. Use this case for export/control finish or reviewer calibration; it is development evidence, and removing its named defects does not automatically establish creativity.


The **editing-frame** case is a working original study with actual licensed/publicly usable material: compare a fixed editing aperture and a fluid crop viewport. The paired captures show settled square and wide crops. [Operate the study](lessons/aperture.html), read its [countercase](lessons/aperture-study.md), and retain the [NASA media provenance](lessons/aperture-provenance.json). Its action-travel measurements do not select the best design for every product. This is authored teaching evidence, separate from autonomous-model benchmarks and human approval.

The **packing-preference** case preserves one user’s blind choice C from three Flash components, with no supplied reason. Compare task footprint, group organization and label hierarchy while observing that the preferred option still contains borders and category counts. This guards against turning scoped anti-slop feedback into a universal style ban. See [the preference record](lessons/packing-preference.json); it is development evidence, not an unseen test.
