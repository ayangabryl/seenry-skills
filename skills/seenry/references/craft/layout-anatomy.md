# Layout anatomy for a disputed composition

Use when layout, alignment, excessive copy or visual hierarchy has been rejected. Work from the rendered content, not a screenshot grid laid over an unrelated template.

1. Identify the reader's task and the first useful object. A component workshop can open with examples; it need not introduce a large marketing hero. A checkout needs commitment context, not a gallery.
2. Mark the actual container edges, reading edge, text baseline, media crop and control center. Separate optical alignment from CSS box alignment. An icon's path may be off-center within a correctly centered viewBox.
3. Mark group membership: label with field, caption with media, price with billing terms, control with the state it changes. Repeated subtitles need distinct information; remove duplicated descriptions before shrinking type.
4. Compare content-to-chrome area. A demonstration must remain readable and operable inside its frame in the largest expanded state. Do not solve an oversized embed by shrinking its controls to illegibility.
5. Test the same relationships at a narrow width and with long content. Columns can change; source order, group identity and useful actions must survive.

An optional anatomy view uses actual implementation measurements and is explicitly labeled as a teaching/debug view. Show only useful guides: container inset, gutter, baseline or crop. Keep debugging chrome out of normal production experiences. The overlay explains current geometry; it does not prove that the composition is effective.

For a neutral palette request, compare actual computed RGB values: near-white with unequal channels is tinted. Preserve purposeful colors in source media separately from interface surfaces. This is a project constraint, not a universal ban on warm palettes.

Before handoff, record the specific rejected treatment, the replacement and what changed in rendered evidence. A cleaner heading is a copy repair, not proof of comprehensive layout competence.
