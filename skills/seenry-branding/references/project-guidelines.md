# Turn the selected identity into usable project rules

Use when creating brand guidelines, codifying an existing identity or maintaining consistency across a substantial project. MCP is optional. Supplied decisions, real implementation and local assets are sufficient to begin; unresolved identity choices remain provisional.

## Establish one source of truth

Inspect existing brand docs, token files, font/asset manifests and shared components first. Preserve the project's naming and format. If no guideline exists, create `BRAND.md` in the project and link it from `DESIGN.md`; use the optional [authoring outline](../assets/BRAND.example.md) only when helpful. Do not introduce a second token store or rebrand a working product while documenting it.

For a new identity, use the main art-direction workflow to select a tested direction before presenting its rules as settled. For codification, derive rules from supplied standards and actual uses; identify contradictions rather than retroactively inventing rationale. Keep inherited requirements, author-selected proposals, implemented rules and user acceptance distinct. Record version/date and unresolved conflicts.

## Write decisions people and agents can apply

| Area | Useful project rule |
| --- | --- |
| Positioning and language | Who it serves, what is true, intended character; actual action, error and recovery wording examples. |
| Marks | Real asset paths, variants and applicable surfaces; declared clear space, minimum sizes and partner use when relevant. If unspecified, propose and test rules rather than claiming official measurements. |
| Color | Link actual semantic tokens; explain canvas, text, action and state roles, permitted pairings and supported appearances. Record tested foreground/background pairs. Separate identity artwork color from UI status. |
| Typography | Link selected font files/licensing; semantic roles, weights, sizes/line heights, measures and responsive behavior; required scripts, numerals and fallback. Examples do not prescribe the same fonts for every project. |
| Composition and controls | Grouping, alignment, density, spacing and corner relationships; existing component variants and when each applies. A brand guide does not dictate identical layouts for different tasks. |
| Material | Actual imagery, crop/focal rules, icon family/weight, illustration or graphic relationships; asset ownership and replacement status. |
| Motion | Link the relevant motion contract: trigger, anchor, transition/result, interruption and reduced-motion equivalent. Distinguish observed behavior from proposed timing. |

Omit inapplicable sections. Document decisions that constrain later work, not a dictionary of design terms. Keep values authoritative in the existing tokens/components; the guide explains their roles and links to them. If a visual table repeats values for readers, regenerate or check it when the source changes. Do not invent CMYK/Pantone equivalents, font coverage, accessibility passes or licensing.

Keep a small codification compact: roughly 300–600 words is a useful starting size when only a brief and a few style rules exist. Group missing decisions and verification limits once instead of repeating them in every section. DESIGN.md should link the guide and record the current task, version and exceptions; do not duplicate the manual. Larger identity systems earn additional detail through real variants and applications, not boilerplate chapters.

## Demonstrate, then maintain

Use the real implementation to show a representative expressive application and a contrasting dense or utilitarian one when the project contains both. Show supported appearances and decisive states where relevant. Pair a rule with a concrete use and a contextual counterexample. Necessary UI focus, boundaries and feedback remain visible; “clean” does not mean removing useful information.

When a visual guideline is requested, build an inspectable page in the existing stack using its tokens, fonts and components. Keep navigation, explanation and specimens clearly separated, with a stable reading structure and enough space to compare actual applications. Reference booklet layout is documentation inspiration, not a landing-page template. Render at ordinary and narrow widths. Do not publish a development guide as customer-facing product content by default.

Give later agents the guide path/version, relevant actual rules, component APIs and selected captures. A restricted context needs the excerpt itself; an inaccessible filename is not guidance. Preserve all unrelated rules during a local change. Record deliberate exceptions and their scope; update source tokens/components and guide together when an intended brand decision changes. Recheck representative affected uses with [design continuity](../../seenry/references/design-continuity.md), actual font loading, state contrast and interaction evidence. Report authored, implemented and verified coverage separately; a neat manual alone cannot prove consistency.

For reference-study examples, read [guideline observations](guideline-observations.md) only when comparing documentation or resolving a rule. No library connection is needed to apply the method.
