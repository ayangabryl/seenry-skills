Imported files can be historical: the examples below are evidence about those versions, not assertions of each brand's current policy. ## Bolt: roles and contextual comparisons

January 2024 manual, credited to Koto in library metadata. Read the supplied text excerpt and visually inspected PDF pages 17–18, with adjacent page portions visible. The type hierarchy page separates a narrow explanatory column from a worked composition containing headline, supporting text, body, annotation and button. The next page compares text/background pairings using repeated content. The useful structure is **rule beside application**, making role differences and color relationships inspectable. Its actual fonts and yellow/gray palette belong to Bolt; they are not Seenry defaults. A printed pairing example still needs contrast testing for an interactive project's real sizes and states. [Seenry reference](https://seenry.design/#/design/43b21cc8b1ffec94454dd2cbfc3508e2).

## Frame.io: identity details and applications

The contents also separate foundational rules from photography and application chapters. Transfer: document the intended context and an actual asset variant, not just a logo image and a palette. Optical exceptions should be explained against the specific mark. ## FIBA Women's EuroBasket: a family of variants

2023 manual, credited in-house. The supplied excerpt describes portrait/landscape and background-dependent mark variants, host-country/city and partner arrangements, and a color reserved for the logo. Transfer: separate the recognizable core from variants permitted for different surfaces and relationships. A project's identity color is not automatically an action or success token. Sporting-event exceptions need not apply to a small product with one mark. This was an excerpt study; the graphical-elements, photography and final application chapters remain unreviewed. [Seenry reference](https://seenry.design/#/design/b8044f79e26356b8c17da0cc4bbab50b).

## Apply without copying the manual

Keep explanation and specimens easy to compare; use stable documentation hierarchy, actual asset variants and specific counterexamples. Test the same rules in different project applications. Preserve what should stay recognizable while allowing task-appropriate composition and density. Documentation can use numbering, large specimens or comparison grids without making those devices the product's visual style. No reference booklet proves the accessibility or behavior of the interface being built. Reuse the project implementation for visual specimens and inspect it before recording a rule as verified.
